# Quality standards

## Engineering

- Use explicit server/client/shared boundaries and small modules.
- Treat all client-originating state as untrusted. Validate remote argument type, bounds, identity, current gameplay state, and rate on the server.
- Keep user-owned state and persistence failure paths explicit. Do not add a DataStore write until schema, retry, idempotency, shutdown, and recovery are designed.
- Use deterministic, bounded tools and surface errors at the boundary where they occur.
- Preserve asset source, license, technical specs, and optimization evidence.

## Evidence grades

| Grade | Meaning | Examples |
|---|---|---|
| Static | Source and configuration inspected; runtime not exercised | Node syntax, heuristic Luau scan |
| Built | Project file generated by the declared build tool | Rojo `.rbxlx` build |
| Studio verified | Real Studio instance was inspected or run with evidence | MCP instance ID, console output, screenshot |
| Device verified | Target hardware or simulation produced measured results | Frame time, memory, input and layout checks |
| Release verified | Release candidate behavior was tested and documented | Certification report with all gates |

Never report a lower grade as a higher one. Static security scans cannot certify a game. A local build does not prove that Studio playtesting or publishing works.

## Current Lab checks

- `npm test` — local API/storage/path/security checks, specialist and task workflows, MCP protocol fixtures, backup compatibility, and (on Windows) three pure Roblox-free Luau CLI specs.
- `scripts/test-all.ps1` — Node suite, pinned Luau syntax parser, and all declared Rojo builds.
- `scripts/doctor.ps1` — current environment inventory.
- `scripts/verify-roblox.ps1` — installation and local prerequisites; live Studio gates remain explicitly untested.

## Luau review checklist

- Server owns rewards, progression, inventory, purchases, match outcomes, and persistence.
- Remotes validate instance ancestry/tag, type, range, ownership, cooldown, permission, and current state.
- Client scripts present information and request actions; they do not decide authoritative outcomes.
- Test both server and client paths, invalid remotes, repeat input, respawn, disconnect, latency, and mobile readability where applicable.
- Profile representative target devices before claiming performance.
